# dsh-agent-bridge audit: structure, technology, packaging, two-way ping

2026-11-17.
Subject: `<repo clone>` main at `91df440` (v0.6.1), live on DSH 0.2.2-rc.3, profile `desktop`.
Method: I read all tracked source (3,225 lines), ran `node --test` (28/28 pass, Node 24), inspected the live profile and the DSH runtime. I did not change anything or touch the live bridge beyond one `dsh_list`.

Severity: **H** high, **M** medium, **L** low. "Verified" means I checked it in code or on this machine. "To verify" means it needs a test or a live check.

---

## 1. Summary

The bridge is small, readable and already free of npm dependencies. Its security basics are sound: loopback only, constant-time bearer check, no CORS, hashed audit, provenance from `requestId` instead of from text. The test suite is good for its size.

The main risks are not in today's code. They are in what Phase 3 will add to it:

1. **`index.js` is one 485-line closure.** Phase 3 adds a mailbox, agents, an inbox, threads and loop limits. Without a split first, that file will triple and become hard to test.
2. **The token is not a boundary between local agents.** Every agent with a shell (DSH, Codex, Claude Code) runs as the same OS user and can read `~/.dsh/agent-bridge.json`. Per-agent tokens (P3.1) give attribution for honest agents, not protection from a hostile one. The plan should say so.
3. **Two plan assumptions are now de-risked.** DSH has an agent-tool API (`ctx.tools.register`), and DSH ships its own Node 24. This makes P3.4 and the "all-in-one" package straightforward.

### Security

| # | Sev | Finding | Fix |
|---|---|---|---|
| X1 | M | **Same-user agents can read the token.** Any agent with a shell tool can read `~/.dsh/agent-bridge.json` and act as any sender with full scopes. Phase 3's claim "the sender name cannot be forged" holds only if the other agents cannot read each other's tokens, and they all run as the same user. | State the threat model plainly: the bridge protects against other OS users and browsers, not against local agents of the same user. For P3.1, disable the `legacy` all-scope token once per-agent tokens exist (with a config switch for migration). Store per-agent tokens in each harness's own config, not in one shared file. Treat scopes as accident prevention and attribution, not as isolation. |
| X2 | M | **Stale state file after a port clash.** If port 7788 is taken, `listen` fails, the old state file stays, and the MCP client sends the bearer token to whatever process owns 7788. On Windows, any local user can bind a loopback port. | On a `listen` error, rewrite the state file as `{stale: true, error}` without the token, or remove it. Optionally fall back to an ephemeral port and write that. `doctor` should flag `stale`. |
| X3 | L | The `Host` header is not checked. DNS rebinding is low risk because a page cannot get the token, but the check is cheap. | Accept only `127.0.0.1:<port>` and `localhost:<port>`. |
| X4 | L | Unauthenticated requests are logged with a client-chosen agent name and shown in the Bridge tab. | Log unauthenticated requests as `unauthorized` with no agent name. |
| X5 | L | On Windows the state and audit files rely on the profile ACL; mode `0600` has no effect. | Set a user-only ACL at creation (P3.1 already plans this for the agents file). Apply it to all three files. |
| X6 | L | CI actions are pinned by tag (`@v4`). In the release workflow, `contents: write` applies to the test jobs too. | Pin actions by SHA. Give `contents: write` to the release job only. Consider `actions/attest-build-provenance` for the tarball. |

## 4. "All-in-one" package: feasibility

**Verdict: feasible and cheap, because the hard part is already done.** The plugin has zero npm dependencies (Node built-ins only). What the user must have installed today:

| Today needs | Why | All-in-one answer |
|---|---|---|
| Node.js ≥ 22 on PATH | The MCP stdio client and `doctor` | **Use the Node that DSH ships.** Verified: `DeepSeek Harness.exe` with `ELECTRON_RUN_AS_NODE=1` runs Node **24.21.0** with `fetch`, and `resources/runtime/versions.json` pins Node 24.21.0 and pnpm 11.28.5. The `dsh.cmd` CLI already starts that way. |
| PowerShell 7 or bash | The install, connect and uninstall scripts | One Node CLI, run by the same bundled Node. |
| GitHub access | Release tarball or tag | Keep it as the default. Add an offline path: `dsh plugin add file:<path>.tgz`, with the SHA-256 checked by the CLI. |
| The `claude` or `codex` CLI | Only to register the MCP server | Unchanged: it is the client's own tool. The CLI can also print the config for a manual paste. |

### Proposed shape

One package, one entry point, `bin/dsh-bridge.mjs`, with subcommands:

``
dsh-bridge install [--source release|local|file] [--version x] [--profile p]
dsh-bridge doctor  [--profile p]
dsh-bridge connect claude|codex|generic [--name n] [--execute]
dsh-bridge mcp                      # the stdio MCP server (today's mcp.mjs)
dsh-bridge watch   [--session id] [--until turn-end|message|pending-input] [--exit]
dsh-bridge agent   add|list|revoke  # Phase 3
dsh-bridge send|inbox|ack           # Phase 3, for agents that have a shell but no MCP
dsh-bridge uninstall [--purge]
``

Plus two small launchers, `dsh-bridge.cmd` and `dsh-bridge` (sh), about 10 lines each. They find a Node in this order: `DSH_NODE`, the DSH install (`%LOCALAPPDATA%\Programs\DeepSeek Harness\DeepSeek Harness.exe` with `ELECTRON_RUN_AS_NODE=1`, or the macOS and Linux equivalents), then `node` on PATH. `connect` writes the MCP config with the absolute launcher path, so the client never depends on PATH.

### Options I do not recommend

- **Node single-executable application (SEA) or `bun`/`deno compile`.** These produce a 60–100 MB unsigned `.exe` that Windows SmartScreen and antivirus tools flag, and they add a build toolchain. They gain nothing over reusing the Node that DSH already ships.
- **Bundling Node inside the plugin.** Same size cost, and it duplicates DSH's runtime.

### Risk

`ELECTRON_RUN_AS_NODE` is a DSH implementation detail; the official `dsh.cmd` relies on it, but it is not a documented plugin contract. The launcher keeps `node` on PATH as a fallback, and `doctor` reports which runtime it used.

**Effort:** about one release (0.6.3 or folded into 0.7.0). It removes about 520 lines of shell, fixes P1 and P2, and makes Windows PowerShell 5.1 irrelevant.

## 5. Other useful improvements

Ordered by value for the cost.

1. **`dsh_wait` returns on pending input** (T2) and **`follow()` reports auth errors** (T3). Small changes that remove the two most confusing silent hangs. Fold them into 0.6.2.
2. **Stale state on a port clash** (X2). Small, and it stops the token from leaking to the wrong listener.
3. **Refactor-only split of `index.js`** (S1, S2) as the first PR of 0.7.0, before the mailbox lands.
4. **`scripts/live-check.mjs`** (S6): the manual live checks as one command against `bridge-test`. It makes every DSH upgrade a single run.
5. **`dsh_result(requestId)`** (already P3.6): once it exists, waits no longer depend on in-memory cursors.
6. **`structuredContent` on MCP tool results** (P4), so clients stop parsing JSON out of text.
7. **A `dsh_status` MCP tool** that returns `/health`, the protocol and the current runtime. An agent can then diagnose "bridge down" versus "token wrong" by itself.
8. **Audit viewer in the Bridge tab** (metadata only), plus `dsh-bridge audit --since 1h` in the CLI.
9. **Inject a note without starting a turn.** DSH agents have `agent.inject(...)` (seen in dsh-codex-subscription). A "low priority" ping could become a context note that the session reads at its next turn, instead of a new prompt. To verify on `bridge-test` before relying on it.

## 6. Two-way ping across harnesses (for example DSH executor ↔ external reviewer)

### What exists today

- **Into DSH:** `dsh_send` starts a turn. It works now.
- **Out of DSH:** only by watching. `watch.mjs` or `dsh_wait` sees the `turn-end` event. A DSH agent cannot address anyone.
- **Claude Code waking up:** only while something is watching, such as a Monitor or background task running `watch.mjs`.

So DSH → Claude Code → DSH already works as a manual relay when Claude Code is actively waiting. It does not work for an **idle** reviewer, and a DSH agent cannot choose whom to ping.

### Design: the bridge as a local post office

``
 DSH executor ──bridge_send(to:"reviewer", kind:"review-request", ref)──┐
                                                                        ▼
                                                ┌─────────────────────────────────┐
                                                │ bridge mailbox (P3.2, on disk)  │
                                                │ thread, hop, auto, budgets      │
                                                │ (P3.7), audit (P3.9)            │
                                                └──────────────┬──────────────────┘
                     wake adapter chosen by the receiver's registration
             ┌──────────────┬──────────────────┼──────────────────┬─────────────┐
             ▼              ▼                  ▼                  ▼             ▼
       DSH session    Claude Code        Claude Code         Codex         any harness
     (prompt/queue    (watch --exit      (MCP task or        (webhook or   (SSE inbox or
      or inject)       → Monitor wake)    channel, later)     exec resume)  webhook)
             ▲
             └──────── reviewer: bridge_reply(threadId, verdict) ── same path back
``

**The message is a ping, not a payload.** Keep the body short (≤ 2,000 characters) and carry a reference: `{threadId, kind, ref: {repo, branch, sha, pr}, summary}`. The receiver pulls the details itself (git, `gh`, `dsh_read`). This keeps messages small, makes them auditable, and limits what an injected instruction can carry.

**Message envelope:**

``json
{
  "id": "msg-…", "threadId": "thr-…", "inReplyTo": "msg-…",
  "from": "dsh:<executor>", "to": "claude-code:reviewer",
  "kind": "ping | review-request | review-result | question | done",
  "ref": { "repo": "FloStyle/dsh-agent-bridge", "sha": "…", "pr": 4 },
  "summary": "0.6.2 ready for review: L1–L3, tests green",
  "hop": 1, "auto": false, "expiresAt": "…"
}
``

**Each receiver registers how it wakes** (P4.7 discovery):

| Harness | Wake method | Status |
|---|---|---|
| DSH session | Prompt in queue mode (P3.3), or `agent.inject` for low priority | Prompt works today. Queue mode and inject: to verify. |
| Claude Code | `dsh-bridge watch --agent reviewer --until message --exit` as a background task or Monitor. When it exits, Claude Code is re-invoked. | Works today with no new client features. **Start here.** |
| Claude Code | MCP task returned by `bridge_inbox(wait)` (P4.2) | Needs MCP task support in the client. To verify. |
| Claude Code | MCP channel `notifications/claude/channel` (P4.4) | Research preview; needs a CLI flag and org enablement. Optional. |
| Codex | Webhook to a local listener, or a non-interactive resume command | Research Codex's resume command before writing code. |
| Any other | SSE `GET /inbox` stream, or a webhook | Generic fallback. |

**How a DSH agent sends.** Use `ctx.tools.register` (verified: dsh-codex-subscription registers its tools this way, and the registration returns a disposer) to give DSH agents `bridge_send`, `bridge_reply`, `bridge_inbox` and `bridge_agents`. This resolves the main open question in P3.4. A second path also exists: dsh-skill-mcp-panel shows that DSH loads MCP servers as `mcp__<server>__*` tools, so the bridge's own MCP server could be registered inside DSH. Prefer `ctx.tools.register`: it runs in-process, so the bridge knows the calling session without a token.

**Walkthrough: executor asks the reviewer, the reviewer answers**

1. The DSH executor pushes branch `0.6.2` and calls `bridge_send({to: "reviewer", kind: "review-request", ref: {pr: 4, sha}})`.
2. The bridge stores it (`queued`), checks the hop limit and budget, audits it, and emits SSE `message` for `reviewer`.
3. The Claude Code reviewer has `dsh-bridge watch --agent reviewer --until message --exit` running in the background. The process prints one JSON line and exits, and Claude Code wakes up.
4. The reviewer calls `bridge_inbox`, reads the reference, reviews the PR with `gh`, then calls `bridge_reply(threadId, {kind: "review-result", summary: "2 findings", ref: {pr: 4}})` and `bridge_ack`. It re-arms its watcher.
5. The bridge routes the reply to `dsh:<executor>`. If that session is idle, it gets a prompt; if it is busy, the reply waits in the queue (P3.3). The executor wakes, reads the review and fixes.
6. Loop safety (P3.7) stops ping-pong. Replies created automatically are marked `auto`, the hop limit is 6, and there is a wake budget per pair per hour. The human can pause everything from the Bridge tab.

### Rules this design must keep

- **A received message is data, not an instruction.** Each adapter delivers it framed as `[dsh-agent-bridge] message from <agent> (thread …)` with the provenance the bridge verified. Receivers must treat it like any other untrusted input; a reviewer never runs commands because a ping said so.
- **No approvals by message.** A ping can say "approval needed in session X" (P3.8). It can never answer the approval.
- **The human sees every thread** in the Bridge tab, and the kill switch stops every wake-up.

### Smallest useful first step (before the full Phase 3)

A "ping-lite" fits into 0.6.x without the mailbox:

1. `POST /ping {to, threadId?, summary, ref?}` appends a `message` event to the existing ring and audit (in memory, so it is lost on restart, and the docs say so).
2. `watch.mjs --agent <name> --until message --exit` lets Claude Code wake on it.
3. One DSH tool `bridge_ping` through `ctx.tools.register` lets a DSH agent send.

This proves the round trip, executor → reviewer → executor, on `bridge-test` within a day. P3.2 then makes it durable. The risk: it adds event types that P3 must keep compatible, so define the `message` event shape now, exactly as above.

2. **0.6.3:** the all-in-one CLI and launchers (section 4), `live-check.mjs`, S4.
